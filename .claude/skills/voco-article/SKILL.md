# VOCO お役立ち記事 作成スキル（v2）

## 目的と役割分担
- voco.co.jp（Studio 製、CMS は Personal プラン）の「お役立ち記事」に載せる原稿を、毎回同じ型・同じ品質で1本仕上げる。
- 人（堀本さん）がやること：最終確認、メイン画像（カバー）の作成、Studio への貼り付け・公開。
- このスキルがやること：テーマ選定、リサーチ、執筆、出稿前チェック、記事中画像（3枚）、Drive / Git / HubSpot への出力、報告。
- 参照ファイル：`content/articles/themes.md`（テーマキュー）、`tools/article/check-article.mjs`（出稿前チェック）、`tools/article/make-image-gemini.mjs`（記事中画像）、`tools/article/make-cover.mjs`（カバー画像。堀本さんが自作するので通常は使わない）。

## 成果物（1記事あたり）
1. `content/articles/out/No.{番号}_article.html` … 正本。先頭の HTML コメントに「タイトル／メタディスクリプション／カテゴリ／H2 に指定する行／画像の位置／CTA 注記」を書く。本文は `<h2> <h3> <p> <ul><li> <ol><li>` のみ。
2. Google ドキュメント `No.{番号}_{タイトル}`（Drive「HP / お役立ち記事」フォルダ、ID `1klA79rJRmpGTfMJZUL5fUFr2ViNZ0Bfj`）… 正本の HTML をそのまま `text/html` で作成。堀本さんはここからコピーして Studio に貼る。
3. 記事中画像 `content/articles/out/No.{番号}_img1.png` 〜 `img3.png` … 必ず3枚作る。環境変数 `GEMINI_API_KEY` があれば写実的なAI画像（`make-image-gemini.mjs`）、無ければフラットイラスト（`make-scene.mjs`）で生成する。どちらで作ったかを報告に書く。
4. HubSpot にブログが存在する場合のみ、同内容を **下書き** で作成（公開はしない）。
5. 報告：Doc の URL、Git のパス、参考にした資料、チェック結果、迷った点。

## 手順

### 0. 準備
- `git pull origin claude/voco-homepage-articles-ys5zwk` で最新化し、`themes.md` と本ファイルを読む。
- Drive フォルダを `parentId = '1klA79rJRmpGTfMJZUL5fUFr2ViNZ0Bfj'` で検索し、既存の `No.xxx_` を控える。

### 1. テーマ選定
- `themes.md` を上から見て、Drive に `No.{番号}_` の Doc が無い最初の行を採用する。
- 全て消化済みなら、既出と重複しない新テーマを1つ決め、報告に「themes.md への追記案」を書く。

### 2. リサーチ（競合の構成を参考にする。文章は写さない）
- WebSearch を 3〜5 回。検索語は「狙う検索語」＋「参考にする競合テーマ」＋「新卒」「中小企業」。
- 参考にする先：新卒採用コンサル・採用代行（RPO）を実際に提供する会社の記事・お役立ち資料（ネオキャリア「みんなの採用部」、マルゴト「まるごと人事」、ワンキャリア採用担当者向け、HRプロ、アールナイン、i-plug、キャリタス、マイナビ／リクルート就職みらい研究所の調査）。
- 見るのは見出し構成・読者が求める論点・よくある結論・統計の出典。**本文の文章は写さない。** 外部の数値は出典（社名・調査名・年）を本文に明記し、確認できない数値は使わない。
- この環境は外部サイトの本文を開けないことが多い。開けなければ検索結果の要約から構成を把握し、無理に取得しない。

### 3. 執筆
**読者**：採用担当がいない、または片手間で採用している中小企業の経営者・総務・人事（50代の社長も含む）。主に関西・東海。

**分量と構造**
- 想定文字数は 2,500 字。実測で ±10%（2,250〜2,750）に収める。H2 は 3〜7 本（「まとめ」を含む）。1 段落は 150 字以内（目安 140 字）。スマホで 8 行を超える段落は読まれない。
- 型：①冒頭2段落で「読者の悩み」→「結論」／②本論（H2 ごとに 300〜600 字）／③「やらなくていいこと」など反対側からの1節（任意）／④まとめ（箇条書き。本文の H2 を全部回収する）／⑤CTA。
- 本文にタイトル（H1）を入れない。Studio 側の記事タイトルが H1 になる。
- Markdown 記法（#、**、-）を本文に使わない。見出しは `<h2>`、箇条書きは `<ul><li>` で書く。
- 「N つあります」と言ったら、直後に ①②③ か箇条書きで数えられるようにする。
- 造語や指標（接触単価など）は初出で完全な式を書く。例：接触単価＝（出展料＋当日の人件費＋交通費）÷実際に話せた学生の数。
- 専門語は初出で1回だけ括弧補足する。例：ナビサイト（マイナビ・リクナビなどの就職情報サイト）、RPO（採用代行）。

**時制（最重要）**
- 記事は数年残る。「今」「現在」「最近」「今年」「来年」「昨年」「今の時期」「今後」「直近」など相対時制の語を本文に書かない。西暦年も原則書かない。
- 時期は卒業年次からの相対で書く。例：「卒業前年の3月に広報解禁」「卒業前々年の夏（大学3年の夏休み）にインターンシップで動き出す」。
- 採用スケジュールは「ルール」と「実態」の2段で書く。ルール：卒業前年の3月広報・6月選考・10月内定。実態：前倒しが常態で、前年の夏インターン、秋〜冬の早期選考、年内内定。

**文体・断定・数字**
- です・ます。盛らない、誇張しない、読者を責めない。
- 断定は射程を示す。「ほぼ例外なく」「絶対」「劇的」は使わず、「私たちが見てきた範囲では」と書く。
- 出典のない「それっぽい数字」（月◯時間、◯割など）を作らない。量ではなく「場面」で定義する。例：「月2〜3時間」ではなく「会社説明の場と一次面接には経営者が出る」。
- 主述を合わせる（「〜と書いた求人は…どの会社も同じに見える」は×。「どの会社の求人も同じに見える」）。
- VOCO の宣伝は本文の1割以下。自社サービスに触れるときは「補足」として付け足さず、読者の判断基準として書く。例：「何人と話せるかが事前に読める場か」を選定基準にする。

**CTA（本文末尾。固定）**
- 段落：「採用のことを、一度話してみませんか。どんな段階でも構いません。「まだ検討中」でも大歓迎です。現場に入って動いてきた立場から、貴社の状況に合わせてお答えします。」
- ボタン2つはコンポーネントで配置するため本文に書かない。HTML コメントで「ボタン：今すぐ無料でプロに相談する／資料3点セットをダウンロードする」と残す。擬似ボタン「［ ］」や全角スペースは使わない。

### 4. 使ってよい VOCO の数字・事例（HP テキスト確定版に準拠。これ以外の社内数字は使わない）
- 年間200回以上のイベント登壇／30都道府県・20業種の支援実績／クライアント総合計40名採用／契約更新率92%
- 採用フルサポート：採用業務の90%以上を担当／契約後に3日〜1週間の業務体験インターン／メイン1名＋サブ1名の固定2名体制／最短半年契約／週1回以上の定例MTG、365日相談対応
- 採用イベント：部活動の公式活動として開催／学生3〜5名のグループ面談形式／3年生中心に20名以上動員／15万〜40万円/回（税抜）・追加料金なし／一般的な大規模イベントは50万〜90万円／開催エリアは北海道・関東・東海・関西中心
- 採用資料作成：ヒアリングから納品まで通常3〜4週間
- 公開事例（この文面の範囲で）：鈴木自工（説明会→面接の歩留まり改善）／MIRAIHOME（採用実務の外注で社内負担軽減・コスト効率向上）／第一カッター興業（自社主導へ、ナビ・人材紹介依存から脱却）／菊谷茂吉商店（初の新卒採用を立ち上げから入社まで一貫支援）
- **使わない**：商談で聞いた個別企業の数字、社内向け資料の表現、未確定セクション「VOCOと組む前に」、他社を悪く言う表現

### 5. 記事中画像（3枚）
- H2 の区切りに 3 枚。位置は「【画像：シーン名】キャプション」の `<p>` を H2 の直前に置く。シーン名は `meeting`（社内会議）／`briefing`（会社説明会）／`interview`（面接）／`event`（合同説明会ブース）／`onboarding`（内定者・入社後のフォロー）／`desk`（担当者の事務作業）から選ぶ。
- 必ずビジネスパーソンが写っている一場面にする（採用のワンシーン、面接、社内会議など）。抽象イラストや風景だけの画像にしない。
- `GEMINI_API_KEY` がある場合：`node tools/article/make-image-gemini.mjs --scene interview --caption "<キャプション>" --out content/articles/out/No.xxx_img1.png` を 3 回。失敗したら下のイラストにフォールバックし、報告に書く。
- `GEMINI_API_KEY` が無い場合：`node tools/article/make-scene.mjs --scene interview --out content/articles/out/No.xxx_img1.png` を 3 回（ブランド配色のフラットイラスト。写真が用意できるまでの暫定）。
- 本文の「【画像：シーン名】」のシーン名は `meeting/briefing/interview/event/onboarding/desk` の英語名も併記する（例：【画像：会議 meeting】）。3枚は同じシーンを重複させない。
- 画像内に文字・ロゴ・実在人物を思わせる表現を入れない。生成画像は `SendUserFile` でチャットにも添付する。
- カバー画像（メイン）は堀本さんが自作する。依頼されたときだけ `make-cover.mjs` を使う。

### 6. 出稿前チェック（必須。NG が出たら直して再実行）
```
node tools/article/check-article.mjs content/articles/out/No.xxx_article.html --target 2500
```
検算項目：文字数 ±10%／H1 なし／H2 3〜7 本／段落 150 字以内／相対時制の語なし／強すぎる断定なし／擬似ボタン・全角スペース・Markdown 記法なし／「N つ」の列挙明示／造語の式／まとめの箇条書きと回収／専門語の初出補足／画像指定 2 枚以上。
「合格」が出るまで出力しない。注意（warn）は報告に転記する。

### 7. 出力
- Git：`content/articles/out/` に HTML と画像を保存し、ブランチ `claude/voco-homepage-articles-ys5zwk` に commit & push（`git pull` してから。push 先はこのブランチのみ）。
- Drive：`create_file`（`contentMimeType: text/html`、`parentId` は上記フォルダ）で Doc を作成。HTML コメントは Doc に出ないので、先頭に「掲載用メタ情報」の段落を付けてから渡す（タイトル、メタディスクリプション、カテゴリ、H2 指定行、画像位置、CTA 注記、参考資料）。
- HubSpot：`LIST_BLOGS` でブログがあれば `CREATE` で下書き（タグは `LIST_TAGS` にある既存名のみ）。**PUBLISH はしない。** ブログが無ければ触らない。
- 途中で失敗しても、できた成果物の URL は必ず報告する。

### 8. 報告の形式
1. Doc の URL／Git のパス（HTML・画像）
2. 参考にした資料（URL）
3. チェッカーの出力（文字数・H2・段落最長・画像枚数・注意）
4. 迷った点、堀本さんに確認してほしい点（数字の妥当性、事例の触れ方など）
5. 画像を生成できなかった場合はその旨と、各プレースホルダーの内容

## Studio へ貼るときの手順（堀本さん向け）
1. CMS →「お役立ち記事」モデル → アイテム追加。タイトル欄に Doc 冒頭のタイトルを入れる（本文にはタイトルを貼らない）。
2. スラッグ `article-{番号}`、カテゴリ、公開日を入力。
3. Doc の本文を貼る。「H2 に指定する行」の一覧を見て、見出しレベルが落ちていたら H2 に直す。まとめはリストブロックにする。
4. 「【画像：◯◯】」の行は削除し、その位置に該当画像（`content/articles/out/No.xxx_img1〜3.png`、または自分で選んだ写真）を入れる。
5. 末尾の CTA 段落の下にボタンコンポーネント2つ（今すぐ無料でプロに相談する／資料3点セットをダウンロードする）を置く。
6. メイン画像（自作）をサムネイル／OGP に設定 → 保存 → 公開。TOP の「お役立ち記事」枠は週1で最新3本に差し替える。
