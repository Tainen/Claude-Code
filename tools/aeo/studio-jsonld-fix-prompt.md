## 0. 守ること

- 触るのは構造化データの設定だけです。**ページの内容・デザイン・CMSの本文・メタ情報（ページタイトル等）は編集しない。**
- **フォームの送信はしない。CMSのフィールドは追加しない。**
- 画面が説明と違う、設定項目が見つからない——このいずれかに当たったら、**その場で止めてスクリーンショットと画面の文言を報告**してください。
- 操作の回避策を試すのは2回まで。

## 1. articleBody を削除する

対象：`/case/consulting/:slug`（お役立ち記事）と `/news/:slug`（ニュース）の構造化データ。

**`articleBody` の行をまるごと削除してください。** 値を空にするのではなく、プロパティごと消します。

理由（作業時の判断材料として）：現在の articleBody は、本文が途中で切れているうえに、ページに埋め込まれたFAQアコーディオンのCSSがURLエンコードされた状態で7,000字以上混入しています。`articleBody` は Google のリッチリザルトに必須でも推奨でもなく、ページ本文は既にHTMLとして正しく出力されているため、削除して問題ありません。

**`articleSection`（見出しの抽出）はそのまま残してください。** こちらは正しい値が入っています。

## 2. 日付をタイムゾーン付きの形式にする

対象：同じ2ページの `datePublished` と `dateModified`。

現在は「年-月-日」の形式で、日本時間の午前9時より前に公開した記事が前日の日付になっています。

**日付のフォーマット指定を、時刻とタイムゾーンを含む ISO 8601 形式に変更してください。** 出力したい形は次のとおりです。

```
2026-09-16T08:52:00+09:00
```

「日付をフォーマット」の指定欄で、次のいずれかができないか試してください。

- ISO 8601 / ISO形式 という選択肢があれば、それを選ぶ
- 書式を文字列で指定できるなら `YYYY-MM-DDTHH:mm:ssZ` または `YYYY-MM-DDTHH:mm:ss+09:00` に相当する指定にする
- タイムゾーンを指定する項目があれば、日本時間（Asia/Tokyo／UTC+9）にする

**どれもできない場合は、無理に変更せず、現在の設定のまま残して「できなかった」と報告してください。** 日付が1日ずれていても、構造化データ全体が壊れるよりは害が小さいためです。試した操作と、画面にどんな選択肢があったかを具体的に書いてください。

## 補足（堀本さん向け・貼らない）

- 報告が来たら全36ページを再実測し、汚染と日付を確認する。
- **articleBody を残す選択肢（埋め込みHTMLの置き方を見直す）は採らない判断。** FAQアコーディオンとCTAのHTMLは21記事すべてに埋め込まれており、これを作り直すのは大仕事。一方 articleBody は Google のリッチリザルトに必須でも推奨でもなく（必須は headline・image・datePublished、推奨は dateModified・author）、新基盤への切り替えで本文はHTMLとして正しく出力されるようになったため、JSON-LD 側で本文を重複させる必要がない。
- **日付の形式が変えられなかった場合は放置してよい。** 1日のずれが検索順位に影響する可能性は低い。ただし「公開日が実際より1日前に見える」ことは残るので、気になるなら記事の公開時刻を午前9時以降にする運用で回避できる。
- 静的ページ11枚には JSON-LD が無いが、優先度は低い。入れるなら `/company` に Organization、`/service/*` に Service。TOP の Organization と重複させない形にする。
